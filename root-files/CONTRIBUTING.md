# Contributing To {{PROJECT_NAME}}

Thank you for helping improve the project.

## Before Starting

- Check existing issues, plans, requirements, and accepted decisions.
- Discuss changes that affect architecture, compatibility, security, privacy,
  or product scope before investing in a large implementation.
- Never include secrets, private data, or unapproved third-party material.

## Making A Change

1. Create a focused change with a clear outcome.
2. Add or update tests at the narrowest honest validation boundary.
3. Update current documentation in the same change.
4. Run the required local checks.
5. Explain user-visible changes, risks, and unsupported cases.

## Documentation Expectations

- Product behavior should trace to an accepted requirement when the project
  uses requirement records.
- Architectural changes require an ADR and may require an Architectural Review.
- Plans do not override accepted design or policy.
- Update guides, tutorials, reference, migrations, and release records when
  their supported behavior changes.
